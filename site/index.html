Features

What you need every day, without the account

An API client that lives in your editor and keeps what you write in your repository: no sign-in, no cap on collections or requests, no cloud to fall behind.

The answer beside the request

One editor for the request, one pane for what came back.

  • Query, Headers, Auth, Body (JSON, text, XML, form, multipart, GraphQL, a file), Scripts, Tests, Settings, Docs and Code
  • The body pretty or raw, pictures too, headers, cookies, tests, the console of your scripts, the request as it was sent, and a timeline of the phases
  • The answer beside the request, or below it as in Postman: two buttons at the top of a request switch it
  • Ctrl+Enter sends; variables are marked known, unknown or dynamic as you type

Collections, folders, environments

Native trees in the side bar, with drag and drop, rename, duplicate, move and filter.

  • A folder or a collection sets what its requests share: base address, headers, authentication, variables, tests, scripts, settings; the nearest wins
  • Environments with secret values; pick one in the status bar
  • Follows your theme and your keyboard: it is the same VS Code, not a web page inside it

Requests are files

One YAML file per request, in your repository, readable in a pull request.

  • Bodies and scripts as blocks, the order of a folder in its file: a change is a few lines
  • Edit by hand if you like (Open as Text); the editor follows
  • A generated .http copy next to each request for REST Client, httpYac and the JetBrains client

Authentication, with OAuth 2.0

Set it once on the collection; requests inherit it.

  • Bearer, basic, API key, and OAuth 2.0: client credentials, password, authorization code with PKCE, refresh
  • Tokens are kept in the secret storage of VS Code, never in a file
  • You are asked before credentials go to a token server for the first time

Tests, captures and scripts

Check the answer, keep a value for the next request, or write JavaScript.

  • One-line rules: status == 200, json $.id exists, token = json $.access_token
  • Scripts before and after a request, in a sandbox (a subset of the Postman pm API), and only after you allowed the exact text
  • Variables that scripts set stay in memory and are never written to a file

Runner, code, cookies, history

The same send, many times, or somewhere else.

  • Run a collection or a folder: passes, a pause, stop at the first failure, a CSV or JSON data file, JSON and JUnit reports
  • The request as cURL, PowerShell, JavaScript, Python, Go, C#, PHP or Java, with the secrets left out
  • Cookies that survive a restart without a value in a list; a history that keeps only a line by default

Built for files that come from other people

  • Nothing runs by itself

    A request file cannot run code, read a file of yours or reach your network. A script needs your yes, for its exact text.

  • Secrets stay out of Git

    Secret values live in files that Git ignores, and are hidden in the history, the code you copy and the reports.

  • Audited, then fixed

    Six independent security reviews attacked the built extension and its importers; what they found is fixed, tested and written down.

Import

Start from what you already have

Each way reads a file or a text, tells you what it found as a count, and writes nothing until you say yes. What could not be carried over is a list of notes, one command away.

FromWhat comes across
OpenAPI or SwaggerA JSON or YAML file, or the address of a program that is running (/v3/api-docs, /swagger.json): a folder for each tag, a request for each operation with its parameters, a body made from the example or the schema, the authentication, a status test, and the servers as environments.
The controllers of your codeThe routes found in the source of the workspace (NestJS, Express, Fastify, Spring, ASP.NET Core, FastAPI, Flask, Django, Laravel, Go and more), with the folders named after the controllers. Read from the text of the code, not by running it.
PostmanCollections v2.0 and v2.1 with folders and their order, requests, authentication, scripts and variables; environments and globals files.
Thunder ClientCollections, folders with what they set, requests and environments, from the data folder or exported files.
cURLOne request from a command you copied from a browser, a document or a terminal.

A credential typed into an imported request, or given as an example in a description, becomes a secret variable of the collection, with its value in a file that Git ignores. Nothing an importer reads is run, the work and the text of one import are limited, and the address of a description is fetched like any request you send, through the same engine. The older converter that writes plain .http files from Thunder Client data is still in the repository.

Files

Plain files you can read, diff and review

The files are the product: there is no database behind them and no export step. A folder of the workspace holds everything, and Git sees it as it sees code.

Layout

api-client/
  workspace.yml                 variables and settings of the workspace
  .gitignore                    keeps the *.local.yml files out of Git
  collections/petstore/
    collection.yml              base address, headers, auth, variables, tests
    collection.local.yml        secret values (not for Git, mode 0600)
    pets/
      folder.yml                what the folder sets, and the order of its requests
      list-pets.req.yml         one request
      list-pets.http            the generated .http copy
  environments/
    dev.env.yml                 the variables of an environment
    dev.env.local.yml           its secrets (not for Git)

A request, as it is on disk

name: Create pet
method: POST
url: '{{baseUrl}}/pets'
auth:
  kind: bearer
  token: '{{token}}'
body:
  kind: json
  text: |-
    {
      "name": "Rex"
    }
tests:
  - expr: status == 201
captures:
  - expr: petId = json $.id

Trimmed: the file also has an id and the schema version. The reader is a strict subset of YAML, so a file from a stranger is data and nothing else.

The .http copy

Next to each request the extension writes list-pets.http for people who use REST Client, httpYac or the JetBrains HTTP Client, or who only read the files in a pull request. The request is the source and the copy is generated from it, one way. It never holds a secret or anything those tools would run or read, and a copy you edited is never overwritten: you can take its edits into the request, see the difference, discard them or keep the file as your own. Turn it off with apiClient.mirror.mode.

Safety

Collections can come from anyone

A cloned repository, the answers of servers and the files of other tools are all other people's data. These are the cases the client is built and tested for.

Files are data

The YAML reader has no anchors, aliases or tags, and limits on size and depth. Paths cannot leave the collection, links are never followed, and what a request sets while it runs belongs to its own collection.

Scripts need your yes

Nothing runs until you have allowed the exact text, kept on your machine and never in the repository. A pull, a branch switch or an import asks again. The sandbox has no files, no network and no Node.

Redirects keep your credentials

A redirect never takes Authorization or a cookie to another origin, never goes from https to http, and never goes from the internet to your machine or network unless you allow it.

Secrets are covered by name and value

Wherever something is written down (history, code, reports, console, the .http copy) a secret is covered by what it is and by what it is called, in the forms it takes in an address or a form.

Git is asked

If a .gitignore of the repository would let Git commit a file with secret values, or one was committed before, the extension asks Git and tells you.

Tested, then attacked

Unit tests, a mutation check that breaks the rules on purpose, real VS Code runs, and three independent security reviews of the built extension. The notes list what they found and what is left.

MIT licensed. Read the source to check any of the above, and the security policy for what is and is not defended against (a script you allowed can read the variables it is given), and how to report a problem.

First request

Open a folder and the API Client icon in the Activity Bar.

  1. New Collection..., then New Request... on it, or Import... a description, a collection or a cURL command.
  2. Type an address and press Ctrl+Enter, or Send.
  3. New Environment... for baseUrl and the like, and use {{baseUrl}}/pets in your requests.
  4. Commit the api-client/ folder.

Requirements

  • VS Code {{VSCODE_MINIMUM}} or newer, and a trusted local workspace
  • Windows, macOS or Linux (Remote SSH, WSL and containers have not been tried by hand)
  • Node.js {{NODE_MINIMUM}} or newer, only to build from a clone

Restricted Mode, the browser and virtual workspaces such as vscode.dev are unsupported: the extension writes files and runs on your machine.

Settings

  • apiClient.root: the folder that holds the files (api-client)
  • apiClient.mirror.mode: the .http copies: on, off or gitignored
  • apiClient.layout: the answer auto (the width decides), below (as in Postman) or beside
  • apiClient.history.mode: metadata, full or off
  • apiClient.scripts.enabled: run scripts after you allowed them

Timeouts, redirects, TLS checking and response limits are set on a request, a folder or a collection, and inherited.

FAQ

Questions, answered from the docs

Is it really free? Is there an account?

It is free under the MIT license, and there is no account, no sign-in, no limit on collections or requests, and no server of ours. The extension sends the requests you send and, for OAuth 2.0, the requests to the token server you configured. It has no telemetry and no update check of its own.

Is this made by Thunder Client, Postman or Bruno?

No. It is not affiliated with or endorsed by any of them. Their names are used only to say which data formats it reads. You can bring Thunder Client data and Postman collections in, and nothing is written into the folders they keep.

Where do my requests and secrets live?

Requests are YAML files in the api-client folder of your workspace. Values of secret variables are in *.local.yml files next to them, which the folder's own .gitignore keeps out of Git; the extension asks Git and tells you if a repository's own rules would commit one. Tokens and persistent cookies are in the secret storage of VS Code.

Can I import an OpenAPI or Swagger file, or find the routes of my code?

Yes, both. Import an OpenAPI or Swagger Description... reads a JSON or YAML file, or fetches the description from the address of a program that is running, and makes a folder for each tag, a request for each operation and an environment for each server. The routes of your controllers are read from the text of the source files of the workspace; since the code is not run, a prefix that a proxy or another file adds may be missing, and the notes say so.

Is it safe to run a script from a collection I did not write?

Only if you read it. A script can read every variable it is given, secrets included, and send them anywhere, so nothing runs until you have allowed the exact text, and any change asks again. The sandbox itself (QuickJS compiled to WebAssembly, in a worker thread, with limits) has no files, no network and no Node, but consent is the only barrier against what the script does with what it is given.

What is missing?

HTTP/1.1 only for now, no WebSocket, server-sent events or gRPC, no digest, AWS or NTLM authentication, no client certificates, no SOCKS or PAC proxy. Collections of ten thousand requests re-read every file when one changes. Remote SSH, WSL and containers have not been tried by hand. The status section lists them.

How is it licensed?

Under the MIT license, copyright 2026 longtd. The license text is in the GitHub repository.

Is the extension on the Marketplace?

Not yet. It is a preview that you build from a clone, as shown in Get started.

Yes: search for {{NAME}} ({{EXTENSION_ID}}) in the Extensions view or open the Marketplace page. It is a preview, so expect rough edges and please report them.

Where do I report a problem?

Open an issue on GitHub Issues. For a security problem, use the private report described in the security policy instead.
