Features

Your requests, in files you own

The importer reads Thunder Client data from disk and writes ordinary text files. Nothing is sent anywhere and nothing is run.

Reads your data directly

Read-only, from the folder Thunder Client keeps on your disk.

  • The v4 layout, the older v3 layout and exported .json files
  • No sign-in and no Thunder Client process needed
  • Never follows a link out of the folder; limits on file size, count, nesting and string length

Folders, order and inheritance

One folder per collection, one file per folder, in the order Thunder Client shows them.

  • Headers, authentication, base URL and tests set on a collection or folder are written into each request, as Thunder Client applies them
  • Disabled parameters and headers stay as comments
  • Path and query parameters, JSON, text, XML, form, multipart and GraphQL bodies

Secrets stay out of Git

Literal tokens, passwords and keys become {{variables}}.

  • Their values go to a private file that is added to .gitignore first and written with mode 0600
  • Encrypted variables are never decrypted: an empty entry waits for you to fill it in
  • Reports and logs name secrets, never show them

Written for the tool you use

REST Client, httpYac or the JetBrains HTTP Client: pick one with --target.

  • Dynamic variables such as {{#guid}} are spelled the way each tool reads them
  • Environment files for httpYac and JetBrains
  • For REST Client, the VS Code command also fills in the REST Client settings for you

Tests become comments

Assertions and captured values survive, as lines every tool ignores.

  • Thunder Client tests become # @assert lines and set-env-var becomes # @capture
  • Scripts are kept as comments and never run
  • There is no runtime for these lines in this project yet

A report of what happened

Every run says what was imported, what was left out and why.

  • IMPORT_REPORT.md lists names and places only, never a value, so it is safe to commit
  • Every finding has a stable TC-… code
  • OAuth 2.0, AWS, digest, NTLM and WebSocket, SSE and gRPC requests are named, not guessed

Careful by default

  • Dry run first

    Without --write you get the report and the list of files, and nothing is written.

  • Nothing is overwritten

    A folder that already has files is never touched: the default writes to api-2 instead. A failure or a cancel half way is undone.

  • Hostile data is expected

    A collection can come from anyone. Its data cannot add a request, read a file of yours or run code when you press Send.

How it works

Three steps from Thunder Client to a commit

The same steps on the command line and in VS Code, where the command is HTTP Files Importer: Import from Thunder Client...

  1. 1

    Point it at your data

    Give it the Thunder Client data folder, exported .json files or your thunder-tests folder if you use Git sync. In VS Code it suggests the folder it finds.

  2. 2

    Read the report

    A dry run shows what would be written, what is left out and why. Cancelling at any step writes nothing.

  3. 3

    Write, then open the files

    Choose the tool, add --write (or confirm in VS Code) and open the .http files. Commit them; the secrets are already ignored.

Output

What it writes

Plain files you can read, diff and commit. The three tools read the same requests but differ in two places, so each import is written for one of them; import again to write for another.

Layout

api/
  <Collection>/
    index.http              requests at the top
    <Folder>.http           requests of a folder
    _bodies/body-0001.txt   a body that cannot stay inline
  http-client.env.json              shared variables
  http-client.private.env.json      secrets (not for Git)
  rest-client.settings.json         REST Client target only
  rest-client.private.settings.json REST Client target only
  IMPORT_REPORT.md                  what was done

REST Client keeps variables in a setting

REST Client does not read http-client.env.json. For that target the importer also writes the variables as a VS Code setting, and the VS Code command fills it in: shared variables to the workspace settings, secrets to your user settings, never synced. Nothing you already have is replaced.

Choosing the tool you write for

Set it with --target or the "Written for" step in VS Code. The default is rest-client.

The other Thunder Client dynamic variables have no exact equivalent: they are left as they are and listed in the report. The b+1 is deliberate: all three tools stop before the upper bound and Thunder Client does not.

Safety

Collections can come from anyone

People share Thunder Client collections, so the importer treats every value in one as hostile. These are the cases it is built and tested for.

Data is never executed

Files are parsed as plain JSON. The core has no network access and starts no process; a test checks that its source and the built extension import neither.

Nothing can add a line

Values on one line cannot carry a line break, free text in comments can never start a directive, and a body is written inline only if no tool would read one of its lines as something else.

Risky body lines move out

A body line that starts with #, //, < or > is read by the tools as a comment, a file include or a response handler. Such a body is saved in _bodies/ and read from there as it is.

Expressions are defused

Text between {{ }} that is not a plain variable name is made harmless. httpYac would run it as JavaScript, and all three tools can read environment variables from it.

Careful writing

Files go through a staging folder and are undone on failure or cancel. Paths cannot leave the target folder, links are never followed and .gitignore is updated before a private file appears.

Tried in the real tools

The output was run against a local server that records what arrives, in REST Client 0.25.1, httpYac 6.16.7 and the JetBrains HTTP Client command line (ijhttp 263.7031), and checked by tests and a mutation check that breaks the rules on purpose.

MIT licensed. Read the source to check any of the above, and the security policy for what is and is not defended against, and how to report a problem.

Command line

Build once, then run the importer. Without --write nothing is written.

git clone {{REPO_URL}}.git
cd api-client
npm ci --ignore-scripts
npm run build

# dry run: the report and the list of files
node dist/cli.js "<Thunder Client data folder>"

# write the files into ./api, for REST Client (the default)
node dist/cli.js "<Thunder Client data folder>" --write

Another tool, another folder

Write for httpYac or JetBrains, into a project folder of your choice.

node dist/cli.js export.json --target jetbrains --workspace ~/my-project --out requests --write

Where Thunder Client keeps its data

In VS Code, under the extension rangav.vscode-thunder-client. For Cursor, VSCodium and others, change Code.

  • Windows: %APPDATA%\Code\User\globalStorage\
  • macOS: ~/Library/Application Support/Code/User/globalStorage/
  • Linux: ~/.config/Code/User/globalStorage/

Command line options

OptionMeaning
--writeWrite the files. Default: a dry run.
--workspace <folder>Folder the files are written in. Default: the current folder.
--out <folder>Folder inside the workspace that receives the files. Default: api.
--policy <p>new-folder (default: a folder that has files is never touched, api-2 is used), skip-existing or overwrite.
--target <tool>rest-client (default), httpyac or jetbrains.
--no-move-secretsKeep literal secrets in the shared files. They are reported.

Exit code 0 means done, 1 the import failed and 2 wrong usage. If you use Thunder Client's Git sync, point the command at your thunder-tests folder.

FAQ

Questions, answered from the docs

Is this made by Thunder Client?

No. It is not affiliated with or endorsed by Thunder Client. The name is used only to say which data format is read.

Do I need Thunder Client installed or signed in?

No. The importer only reads files on disk, so it works on a copy of the data folder or on exported .json files. It never writes into the folder it reads.

How is it licensed?

Under the MIT license, copyright 2026 longtd. The license text is in the GitHub repository.

Which tool should I choose?

The one you will open the files in. All three read the same requests. REST Client keeps its variables in a VS Code setting, which the VS Code command fills in for you; httpYac and the JetBrains HTTP Client read http-client.env.json. If you change your mind, import again with another target.

Are my secrets safe?

Literal tokens, passwords and keys are replaced by variables and their values go to private files that are added to .gitignore before they appear. They are found by name: in headers, query and form fields, path parameters, the password or token in a URL, and inside JSON, XML, query-string and GraphQL bodies. A token with no name next to it, such as free text in a body, cannot be recognised and stays, so read the bodies of a collection you did not write before you commit them. The report and the logs name secrets and never show them. With the REST Client target, the secrets go to your user settings, which the importer also excludes from Settings Sync.

Your original Thunder Client data is not changed, so delete it yourself when you are done with it.

Do the # @assert lines run?

Not by anything in this project. They are comment lines that all three tools ignore, so the request still runs. A runtime that understands them could check responses and chain values; the grammar is in the specification.

Has it been tried on real Thunder Client data?

Not yet on a real v4 folder. It was built from public information and a reading of the extension's code, and tested with data made up to match it. Fields it does not know are skipped silently. If your data imports wrongly, open an issue with the output of tools/thunder-structure.cjs, which prints the structure of your data and no values.

Is the extension on the Marketplace?

Not yet. It is a preview that you build from a clone, as shown in Get started.

Yes: search for {{NAME}} ({{EXTENSION_ID}}) in the Extensions view or open the Marketplace page. It is a preview, so expect rough edges and please report them.

Where do I report a problem?

Open an issue on GitHub Issues. For a security problem, use the private report described in the security policy instead.
